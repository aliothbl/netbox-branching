## Decisões
- **DEC-1 — helper único `_transition_status(expected, new, **fields)`** (`UPDATE ... WHERE pk AND status IN expected`). Aplicado na entrada de sync (READY→SYNCING), merge (READY→MERGING), revert (MERGED→REVERTING) e migrate (READY|PENDING_MIGRATIONS→MIGRATING), em todos os rollbacks (só voltam se o status ainda for o transitório deste job) e nas transições finais (SYNCING→READY com `last_sync`, MERGING→MERGED com `merged_time`/`merged_by`, REVERTING→READY, MIGRATING→READY/FAILED).
- **DEC-2 — transição final sem `save()` do status.** O status e os campos de ciclo de vida vão no UPDATE condicional; depois `save(update_fields=[...])` só com os outros campos, para os receivers de `post_save` continuarem disparando sem reescrever o status.
- **DEC-3 — F14:** `post_save.disconnect(record_applied_change)` em `finally` no merge e no revert.
- **DEC-4 — provision só a partir de NEW.** `provision()` faz o CAS NEW→PROVISIONING antes de criar qualquer coisa. Um 2º job de provision (retry do rq, reenfileiramento) levanta `BranchStatusChanged` sem tocar no banco. Antes ele tentava recriar o schema, falhava e o caminho de falha fazia `DROP SCHEMA` do schema que o 1º job tinha construído. As transições finais também passaram a ser condicionais (PROVISIONING→FAILED, PROVISIONING→READY): um branch resetado pelo recover durante o provision continua FAILED. Dois testes de view marcavam o branch como READY antes de chamar `provision()` (atalho sem sentido); agora partem de NEW, como o fluxo real.
- **DEC-5 — archive: CAS antes do `DROP SCHEMA`, a partir de um status sem job.** Ordem nova, na mesma transação: CAS de `ARCHIVABLE_STATUSES` (NEW, READY, PENDING_MIGRATIONS, MERGED, FAILED) para ARCHIVED → `deprovision()` → evento. O UPDATE condicional trava a linha do branch, então um revert/sync/merge que ainda não começou espera e depois encontra ARCHIVED; um que já está rodando (REVERTING etc.) faz o archive abortar sem apagar o schema. Antes, um archive concorrente com um revert apagava o schema no meio do revert, e dois archives geravam dois eventos ARCHIVED. O modelo continua aceitando os mesmos status de antes, menos os transitórios (a UI e a API já restringem a MERGED). A API e a view tratam `BranchStatusChanged` com a mesma resposta de "não está merged" (400 / mensagem de erro), sem mudar o contrato. O auto-archive já captura a exceção e segue para o próximo branch.
- **Pendente do escopo:** as ações da API continuam respondendo 400 (não 409) quando o branch não está no status esperado. O duplo clique já é coberto pelo CAS no modelo: o 2º job aborta sem efeito. Trocar 400 por 409 muda o contrato público e fica para decisão do owner.
