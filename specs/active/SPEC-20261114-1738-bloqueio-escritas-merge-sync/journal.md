## Decisões
- **DEC-1 — lock de sessão na conexão default, não `pg_advisory_xact_lock`.** Um request de escrita no branch atravessa várias transações em mais de uma conexão (schema do branch + default), então o lock é de sessão, tomado pelo middleware antes da view e solto no fim do request (`finally`). O lock de transação da SPEC original não cobriria o request inteiro.
- **DEC-2 — o request não espera o lock: `pg_try_advisory_lock_shared`.** Se uma operação já segura o lock exclusivo (está lendo o changelog), a escrita recebe 503 retryable na hora (SPEC-1741), em vez de bloquear um worker por toda a duração do merge.
- **DEC-3 — status relido sob o lock.** `get_active_branch()` leu o status antes do lock; um merge pode ter trocado o status e estar esperando justamente este lock. O middleware relê o status depois de pegar o lock e recusa se não for READY.
- **DEC-4 — ordem no merge e no sync: status → lock exclusivo → leitura do changelog.** Antes: leitura → status. O lock exclusivo é tomado num savepoint com `lock_timeout` local (`write_drain_timeout`, padrão 300 s); estourar devolve o branch a READY e falha a operação (`BranchWriteLockTimeout`).
- **DEC-5 — só métodos não seguros (POST/PUT/PATCH/DELETE) tomam o lock.** Leituras não precisam (escopo da SPEC). Escritas fora de request HTTP (scripts e jobs com `activate_branch`) não são cobertas: limitação registrada.
- **DEC-6 — a verificação do fim do merge compara mudanças do branch, não ObjectChange × AppliedChange.** O AppliedChange liga o branch às ObjectChanges que o merge cria **no main**, e as duas contagens não batem por construção: o squash colapsa várias mudanças do mesmo objeto numa só, e o iterative pode gerar mudanças a mais (efeitos colaterais) ou a menos. A invariante que importa é outra: toda mudança no schema do branch fez parte do merge. Dentro da transação do merge, antes do commit, o total de ObjectChanges do branch é comparado com o changelog lido no início. Se houver mudanças a mais (escrita fora de request HTTP, que não toma o lock da DEC-5), o merge falha, a transação volta, o branch fica READY e um novo merge leva tudo.
- **DEC-7 — proteção do `DROP SCHEMA`: mudanças com `time > merged_time`.** Na mesma transação do archive, depois do CAS (SPEC-1737 DEC-5) e antes do `deprovision()`, `_changes_after_merge()` conta as ObjectChanges do schema do branch registradas depois do merge (direto em SQL, na conexão default; branch sem `merged_time` ou sem schema conta 0). Se houver, o archive falha sem apagar nada, com a orientação de reverter e mergear de novo ou deletar o branch para descartar. A exceção é `BranchHasUnmergedChanges`: a API responde 400 com a mensagem (mesmo código dos outros "não pode arquivar"), a UI mostra a mensagem como erro, e o auto-archive registra o erro e segue para o próximo branch. Sem campo novo: o revert zera o `merged_time`, então um branch revertido e remergeado usa o tempo do novo merge. Limitação: uma escrita fora de request cuja transação começou antes do `merged_time` e commitou depois da verificação da DEC-6 tem `time` anterior ao merge e não é detectada. É uma janela de milissegundos, entre a verificação e o commit do MERGED.
