## Decisões
- **DEC-1 — alternativa (a) da SPEC, com a margem guiada pelo banco.** Em vez de uma margem fixa adivinhada, o sync lê em `pg_stat_activity` o início da transação aberta mais antiga (qualquer transação, com ou sem xid: a que ainda vai salvar já está aberta) e grava a marca d'água `min(início do sync, essa transação) − sync_watermark_margin` (em `sync_watermark`, ver DEC-5) (padrão 5 s, para diferença de relógio NetBox × PostgreSQL). A alternativa (b) (xmin/snapshot) foi descartada: o `xmin` de 32 bits não converte com segurança para o `xid8` de `pg_visible_in_snapshot`, e o VACUUM congela o `xmin`.
- **DEC-2 — deduplicação com `SyncedChange`** (nova tabela, migração 0010; branch + ObjectChange do main, únicos). Cada sync registra o que aplicou; `get_unsynced_changes()` exclui isso, e as linhas mais antigas que a nova marca d'água são podadas no fim de cada sync (a tabela fica do tamanho da janela de sobreposição). Sem isso, reler a janela reaplicaria um UPDATE antigo do main por cima de uma edição posterior no branch.
- **DEC-3 — look-back limitado a 1 h** (`SYNC_WATERMARK_MAX_LOOKBACK`). `last_sync` também define a validade do branch (stale): uma conexão esquecida "idle in transaction" por horas não pode envelhecer o branch. Limitação: uma mudança salva numa transação aberta há mais de 1 h e commitada depois do sync ainda se perde.
- **DEC-4 — `pg_stat_activity` precisa enxergar as outras sessões:** com um único usuário de banco para o NetBox (o normal), a coluna `xact_start` das sessões do mesmo usuário é visível. Com usuários diferentes, o papel precisa de `pg_read_all_stats`; sem isso, o comportamento cai no anterior (marca d'água = início do sync − margem).
- **DEC-6 — F4: `ChangeDiff.current` acompanha o main também em SYNCING, MIGRATING e PENDING_MIGRATIONS** (`CHANGE_DIFF_TRACKED_STATUSES` em `signal_receivers.py`; antes, só READY). MERGING e REVERTING ficam de fora, porque as mudanças globais nesses status são o próprio merge ou revert. O conflito no merge já sai do `ChangeDiff.conflicts` (o endpoint de merge recusa com 409 quando há conflitos e `acknowledge_conflicts` não foi passado). O F4 era só o `current` não ser atualizado durante o sync, então o conflito não aparecia.
- **DEC-7 — F15: progresso do sync commitado com os dados do branch.** O sync escreve no schema do branch pela conexão do branch, e a contabilidade (SyncedChange, ChangeDiff, watermark) pela conexão default, com dois commits sem 2PC (o `PREPARE TRANSACTION` exige `max_prepared_transactions` > 0, que vem 0 por padrão). As duas conexões são do **mesmo banco**, então `_record_sync_progress()` grava SyncedChange e `sync_watermark` pela conexão do branch, em SQL com o nome do schema do main explícito (o `search_path` da conexão do branch põe o schema do branch na frente). Assim eles entram na mesma transação das mudanças que descrevem. Na conexão default ficam ChangeDiff/baselines e a poda dos SyncedChange antigos: perder esse commit deixa conflitos desatualizados até a próxima mudança do objeto e linhas a mais que o próximo sync poda, mas nada é reaplicado. Antes, perder o commit default fazia o próximo sync reaplicar tudo, e cada CREATE falhava ("Site with this ID already exists"), travando o sync do branch para sempre.
- **DEC-8 — watermark monotônico (bug da DEC-1, achado no teste do F15).** O watermark de um sync = início − margem pode cair **antes** do limite inferior que o próprio sync usou para ler (`sync_watermark or last_sync or created`). Isso acontece quando o sync roda dentro da margem do provision (o `last_sync` do provision é o fim dele). O sync seguinte relia mudanças anteriores ao provision, que o snapshot já tinha copiado, e falhava nos CREATEs. Agora `watermark = max(calculado, limite inferior atual)`. Isso não afeta o F3: uma transação aberta durante um sync já tinha puxado o watermark daquele sync para trás.
